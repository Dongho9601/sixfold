# Sixfold

Sixfold (`sixfold`) is a free, non-commercial, competitive 100-roll weighted-dice game. Gold has no monetary or material value. There are no advertisements, payments, donations, cash-out, or monetary/material prizes. TypeScript, HTML/CSS/SVG, Vite, a small Node HTTP server, and a persistent SQLite leaderboard. No cloud account, external assets, or service credentials.

## Run locally

Use a supported Node.js LTS release meeting the **22.16+** minimum; the current LTS check used **24.21.0**. From this directory:

```sh
npm ci
npm run dev
```

After installation, **`npm run dev` is the only startup command**. It serves the browser client, API, and database at **http://localhost:5173** by default. If that port is busy, development startup tries the next available port (up to 20 additional ports) and prints the actual URL. Open the URL printed by the new command. Keep the command running while playing. The development server listens on all IPv4 interfaces and prints a **Network** URL at startup. To play on a phone connected to the same Wi-Fi, open that URL (for example, `http://192.168.1.185:5173`). On the phone, `localhost` refers to the phone itself, so use the computer's network address instead.

If the Network URL cannot connect, check that the computer's firewall permits incoming Node.js connections and that the Wi-Fi is not a guest network that isolates devices. Restart the server after changing its host or port configuration.

For an isolated local check of the built client (HTTP is explicitly permitted only for this check):

```sh
npm run build
PUBLIC_ORIGIN=http://localhost:5173 ALLOW_INSECURE_HTTP=true npm start
```

`HOST`, `PORT`, and `DB_PATH` can override the bind address, port, and database file. Example: `PORT=5174 DB_PATH=./data/demo.sqlite npm run dev`. An explicit `PORT` and all `npm start` runs require that exact port; a conflict exits cleanly with instructions to stop the existing server or choose a different port. Use `HOST=127.0.0.1 npm run dev` for access only from this computer. `npm start` binds to loopback by default; use `HOST=0.0.0.0 npm start` for network access to the built client. All records live in the SQLite files under `data/`; keep this directory to preserve games and scores across server restarts. A browser cookie identifies the player. Clearing that cookie creates a new player; it does not remove the previous record. Production additionally requires `PUBLIC_ORIGIN`; the public hosting settings are below.

## Public hosting and operations

Use one Node process and one local persistent SQLite database. The closure checks passed on **Node 24.21.0 LTS**, bundled **SQLite 3.53.4**, npm **11.19.0**, and **macOS arm64**; the earlier preparation used Node 26.4.0 / SQLite 3.53.2 / npm 11.17.0 on the same platform. Node 24.21.0 is listed as LTS by the [Node.js release page](https://nodejs.org/en/blog/release/v24.21.0). `package.json` requires Node 22.16 or later (the backup API starts there), but the minimum version has not been separately tested. **Linux verification remains blocked:** no local container/VM runtime or existing repository CI workflow/runner was available. The native LTS results do not establish Linux compatibility. Run the checks below on the selected Linux image before launch. Hosting has not been selected and no deployment has been performed.

Build with the locked dependencies, then run the same-origin client and API behind HTTPS termination:

```sh
npm ci
npm test
npm run build
PUBLIC_ORIGIN=https://your-domain.example HOST=127.0.0.1 PORT=5173 DB_PATH=/absolute/persistent-dir/sixfold.sqlite npm start
```

The example domain and persistent path are placeholders. Development serves Vite middleware and HMR; public hosting must use `npm start`. `tsx` is a runtime dependency; Vite, TypeScript, and Playwright are development dependencies. A deployment may build with all dependencies and then use `npm ci --omit=dev` in its runtime directory with the built `dist/`, `server/`, `scripts/admin.ts`, and `src/config.ts`/`src/types.ts` files. Preserve the lockfile and installed dependency license files. The application has no service credentials or application secret environment variable; session cookies themselves are credentials.

| Variable | Default / purpose |
|---|---|
| `PUBLIC_ORIGIN` | Required for production. One exact browser-facing origin, normally `https://your-domain.example`; no credentials, path, query, or fragment. Pins action Origin checks and `Secure` cookies independently of forwarded headers. |
| `HOST` | `127.0.0.1` in production, `0.0.0.0` in development. Use an explicit private bind address when a separate proxy/container requires it, and restrict direct access. |
| `PORT` | `5173`; integer 1–65535. Production and explicit ports never silently fall back. |
| `DB_PATH` | `data/one-of-six.sqlite`, relative to the working directory unless absolute. Must be outside `public/` and `dist/`, including symlinked paths. Use a stable persistent path across releases. |
| `TRUST_PROXY_IPS` | Empty. Exact comma-separated IP addresses of the immediate trusted proxy only; no wildcard, subnet, or hop-count trust. IPv4-mapped loopback is normalized to `127.0.0.1`. |
| `STATIC_COMPRESSION` | `true`. Serve build-time `.br`/`.gz` variants. Set `false` when the proxy owns static compression. |
| `ALLOW_INSECURE_HTTP` | `false`. A production `http://` origin requires explicit `true` for local verification. Public hosting requires HTTPS. |

The proxy must terminate HTTPS, preserve the configured public Origin on browser requests, and route both the site and `/api/` to the same origin. The server ignores `Forwarded`, `X-Forwarded-Host`, and `X-Forwarded-Proto`. Secure-cookie decisions come exclusively from `PUBLIC_ORIGIN`. With `TRUST_PROXY_IPS` set, the immediate proxy must **overwrite** `X-Forwarded-For` with one validated client IP; missing, malformed, or comma-separated chains are rejected. For a loopback proxy an example is `TRUST_PROXY_IPS=127.0.0.1,::1`. Do not trust a public client’s supplied address, and do not expose a route that bypasses that proxy. Review the host’s forwarded-header behavior before enabling trust. TLS certificates, redirects, HSTS, and any distributed/bulk-abuse protection belong at the chosen HTTPS layer.

Session cookies retain their existing name, are host-only, HttpOnly, SameSite=Lax, scoped to `/`, and last at most one year from creation. HTTPS public origins add Secure. State-changing requests require the exact same origin and JSON; browser cross-site API reads cannot create sessions. No permissive CORS headers are returned. Errors do not include stacks or database details. The API accepts no authoritative bankroll, probability, payout, or score fields. Modern pending actions bind to the cookie’s player even if another tab replaces that cookie. Earlier unbound saved requests remain supported for continuity; recovery refuses them when a new cookie is created.

API bodies are limited to **16 KiB of bytes**, with valid UTF-8 JSON, exact methods/media types, known fields/actions/targets, canonical decimal revisions of at most 128 characters, request IDs of 16–100 ASCII word/hyphen characters, and normalized nicknames of 1–24 visible Unicode characters (raw input at most 192 UTF-16 code units). Wagers remain exact decimal strings and may use the whole bankroll; a digit length already exceeding the bankroll is rejected before BigInt conversion. There is no gameplay balance/score cap. The HTTP layer permits at most 64 active requests and 256 connections, bounds headers to 8 KiB, times out request bodies after 10 seconds and requests after 15 seconds, and keeps idle connections for five seconds.

| Limit | Burst and sustained allowance |
|---|---|
| New sessions per client IP | 60 initial sessions; replenish one every 30 seconds. Resuming an existing session does not spend this allowance. |
| Actions per player | 30 initial actions; replenish 10 per second. Includes retries and invalid actions. |
| State/leaderboard reads per player | 60 initial reads; replenish two per second. |
| API network guard per client IP | After route/method/origin validation: 600 initial requests; replenish 50 per second, allowing multiple normal players behind one network. |

Rate limits return `429` with `Retry-After` and JSON retry information. Limiter storage has at most 10,000 entries. Entries idle for 30 minutes become eligible for incremental cleanup during later API requests; without further traffic they remain only in process memory until restart. Exhausted storage fails closed with `503` and a retry delay instead of evicting active limits. Limits reset on process restart and do not establish bot-proof or distributed-abuse protection. They are deliberately broad for normal play and shared networks; monitor observed rejections before changing them.

`GET /healthz` (or HEAD) checks the open database with `SELECT 1` and returns only `{"status":"ok"}`. It sets no session cookie and is not cached. Use it for process readiness. SIGTERM/SIGINT stop acceptance, drain active requests, close Vite in development, and close SQLite; after 10 seconds any remaining HTTP connections close. A committed action with a lost response still has its receipt. Configure the process supervisor to allow more than 10 seconds for graceful shutdown, and to restart an exited process. Do not run multiple gameplay workers against this deployment merely to increase throughput; the intended operating model is one instance.

Production static serving inventories only `index.html`, `about.html`, `favicon.svg`, and supported hashed files under `assets/`. It rejects symlinks and does not serve repository files, source maps, secrets, database files, arbitrary `public/` copies, or requested compression sidecars. Files stream rather than being fully read for each request. Hashed assets use a one-year immutable cache; HTML/favicon use content ETags and revalidation. Personalized API reads use `private, no-cache`, cookie variation, and ETags; cookie creation, mutations, errors, and health use `no-store`. Bypass shared/CDN caching for all `/api/` paths and cookie-bearing responses. The build precompresses HTML, JavaScript, and CSS using Node’s zlib. Encoded responses must not be compressed a second time. The proxy may compress JSON API responses and serve static compression instead when `STATIC_COMPRESSION=false`; compression was not benchmarked at any real proxy.

### Persistence, backup, and restore

Put the database on a writable **local persistent filesystem**, alongside its `-wal` and `-shm` files. Do not use an ephemeral release directory or a network filesystem with unverified SQLite locking semantics. SQLite remains in WAL mode with `synchronous=FULL`, foreign keys enabled, and a five-second busy timeout. One connection is reused by the server. New data directories use mode 0700 and database/backup files use 0600; also set suitable directory ownership and access restrictions on the host. Do not put the directory or backups in any web root.

Copying only a live `.sqlite` file can miss committed WAL data. The local backup command uses the SQLite online backup API and checks integrity; it never overwrites an existing destination. It opens the source read-only and accepts older schema versions, so use this command from the prepared release **before the first schema-4 upgrade**. Backup does not migrate or reinterpret records; the other administrative commands require the matching schema:

```sh
DB_PATH=/absolute/persistent-dir/sixfold.sqlite npm run admin -- backup /absolute/private-backups/sixfold-2026-10-10.sqlite
```

Create the private backup directory first. Keep off-host copies through the host’s existing backup facilities, with restricted access; snapshots contain player data and replay receipts. A small starting policy is seven daily and four weekly snapshots, rotated by the operator rather than an application background job. Check backup success and available disk space. Regularly rehearse restoration in a separate directory with the matching release.

To restore, stop the application and ensure no other process has the database open. Preserve the old database and all its journal files together. Copy a verified standalone backup to a **new, empty persistent directory** with a new `DB_PATH`, set ownership/mode, and start the matching release against it. This avoids mixing an old WAL/SHM with a restored database. Verify health, saved state, leaderboard, and a stored-action replay before reconnecting clients. The automated restore checks cover a backup taken while the original WAL database remains open, copying it into an isolated new directory, identical replay of its existing receipt, a new action, another restart, and replay of both receipts. The source database and backup stay unchanged by actions in the restored copy.

Restoring an older snapshot loses every game change, score, moderation flag, and retry receipt committed after that snapshot. Consequently it cannot guarantee consistency with post-snapshot browser actions or stop all such old requests from settling again. Keep the restored service isolated while deciding how to reconcile those clients; prefer a forward fix that retains the current database. A schema downgrade or compressed receipts may also be unreadable by an older release. A code rollback requires a compatible database; otherwise the pre-upgrade snapshot and its data-loss limitations apply.

### Storage accounting and maintenance space

Count the live `.sqlite`, `-wal`, and `-shm` file lengths, every retained backup, and any separately restored copy. `PRAGMA page_count × page_size` (available through `admin info`) measures the logical database, including committed pages still represented in WAL; the main file alone may understate it while the server is running. Backups made by the online API include those committed pages. Backup inspection can leave an empty WAL and an SHM file beside the snapshot; copy the generated standalone database into an empty restore directory, rather than bringing those inspection sidecars along. Filesystem allocation, snapshots, quotas, and backup-provider overhead can exceed these file lengths.

The fixed closure workload began with a **28,672-byte** schema-only database, created ten players and **1,000 new roll actions**, and retained all **1,000 receipts**. After clean close/checkpoint the database was **2,002,944 bytes**, a growth of **1,974,272 bytes** above its initial size (about 1,974 bytes per action including player creation). While open, the largest sampled main/WAL/SHM total was **5,942,800 bytes**; the live backup database was **2,002,944 bytes**, with an additional **32,768-byte** inspection SHM at measurement. This is one macOS LTS sample with random outcomes, not a storage cap or a host capacity estimate. The [closure evidence](docs/benchmarks/release-candidate-closure.json) records every component, settings, and method. The earlier seeded benchmark files are preserved separately.

Plan free space before each maintenance operation:

- **Online backup:** allow at least one full logical database for each new destination, plus ongoing live WAL growth and retained snapshots. Seven daily and four weekly full snapshots require the sum of eleven snapshot sizes, not one database size. Account for off-host copies separately.
- **Restore rehearsal:** retain the current live database and journals and the snapshot; allow another complete database in the new restore directory, its new WAL/SHM, and test-write growth.
- **Receipt compaction:** keep the pre-maintenance backup and allow the batch's updates to append to WAL. It does not guarantee immediate file shrinkage, and there is no universal byte bound per batch. Use measured journal growth and leave headroom rather than assuming saved JSON bytes become free filesystem space.
- **Offline VACUUM:** after a backup and clean shutdown, reserve **up to twice the current database size as additional free space** for the temporary database and rewrite journal, as described by [SQLite's VACUUM documentation](https://sqlite.org/lang_vacuum.html). A fresh backup on the same filesystem consumes another full snapshot before that reserve; allow operational margin as well. Restart a later compaction scan at cursor `0` after VACUUM, because SQLite can change implicit receipt rowids. Complete receipts and their request IDs remain intact.

The default automatic WAL checkpoint threshold was measured at 1,000 pages of 4,096 bytes. That is a checkpoint trigger, **not a hard WAL size limit**: readers can delay checkpoint progress and maintenance transactions can grow the journal. Monitor actual file sizes, free pages, free filesystem space, and checkpoint busy results. Never manually discard a live WAL or remove replay receipts to relieve disk pressure.

For a reproducible bounded check on a built release, run `node --import tsx scripts/release-check.ts`. It accepts no database path or public URL, overrides inherited database/network settings with isolated temporary paths and localhost, starts/stops the production server, restores a generated backup, and measures the fixed new-action workload. To verify the runtime dependency boundary, copy the release into a separate directory, include this verification script alongside `scripts/admin.ts`, run `npm ci --omit=dev` there, then run the same command. Results include whether Vite, TypeScript, and Playwright are absent. Do not run a build from that runtime-only directory. Linux must run `npm test`, `npm run build`, and this production-only check on the selected LTS image before release; the current closure has not executed those commands on Linux.

### Moderation, retention, and upgrades

Moderation is local, requires filesystem access to the database, and has no public HTTP endpoint. Use the public player ID shown by `/api/leaderboard`, never a session cookie:

```sh
DB_PATH=/absolute/persistent-dir/sixfold.sqlite npm run admin -- hide PLAYER_ID
DB_PATH=/absolute/persistent-dir/sixfold.sqlite npm run admin -- show PLAYER_ID
```

Hiding excludes that player from all leaderboard ranking/context queries, survives restarts and nickname changes, and preserves their game, score, session, and complete receipts. Showing restores the entry and its current name. This handles individual abusive entries; creating accounts, an administration dashboard, and automated content classification are outside this release’s scope.

Player data, session hashes, and accepted-action receipts are retained indefinitely for continuity and replay safety. There is no automatic deletion of existing or inactive players. Receipts are **never expired or deleted** by maintenance. Instead, a local command losslessly gzip-packs complete responses in batches, retaining every request ID, fingerprint, and original response:

```sh
DB_PATH=/absolute/persistent-dir/sixfold.sqlite npm run admin -- compact 1000 0
```

The output gives `nextAfterRowid` and `moreMayRemain`; use that cursor for the next batch until complete. Rows already compressed are skipped. Run this outside busy periods using the host’s existing scheduler only if needed, or run it manually. Each invocation examines at most 1,000 rows and holds only that batch; compression happens before its short update transaction. Compaction frees payload space for reuse but does not necessarily shrink the file. If measured free space warrants it, take a backup, stop the service, and run SQLite `VACUUM` offline with adequate extra disk space. `npm run admin -- checkpoint` attempts a WAL truncation at a quiet time; check its busy result. Neither task changes durability settings or removes replay protection. The application emits no access/action log, and internal request-error logs contain only a constant category. Configure bounded retention for supervisor/proxy logs and backups; redact cookies, forwarded credentials, and action bodies.

Before an upgrade, run checks and build in a separate release directory, stop/drain the old process, and take a verified backup. Keep the data path fixed, start the new build, and check health plus a resumed session. Deploy the complete `dist/` atomically and restart the process rather than overwriting assets under a running server. Existing tabs using older hashed assets may need a reload after an upgrade; retaining the prior hashed assets for a transition avoids failed asset loads. Schema 4 preserves competition saves; nonempty pre-competition databases and unknown newer schemas fail closed. Keep the old release and snapshot for investigation; do not silently reset incompatible data.

For basic monitoring, check process CPU/RSS, restarts, p95 API latency, 429/503 rates, database/WAL/free-page growth, filesystem free space, and backup age. `npm run admin -- info` reports aggregate storage counts and page sizes without identifiers; its count queries belong outside latency-sensitive requests. Before increasing capacity, measure the actual runtime/filesystem and representative concurrency, check query plans, shared-network throttling, WAL checkpoints and disk latency, and run the local workload. The current localhost measurements are in [the verification report](docs/VERIFICATION.md); they do not establish a player capacity or a hosting service-level guarantee.

## Play

Columns are labeled **1st 2**, **2nd 2**, and **3rd 2**, covering 1–2, 3–4, and 5–6 at ×3. Rows are labeled **Odds** (1, 3, 5) and **Evens** (2, 4, 6) at ×2.

The initial selected amount is 10 G. Enter any exact whole amount. Tap any target to add that amount; wagers on the same target combine. The amount field accepts exact whole numbers. The + / − buttons and the ↑ / ↓ keys while the amount control is focused change the selected amount by 5 G, down to 1 G. Outside text fields, W decreases and E increases the amount by 5 G; 1 / 2 / 3 recall the three recent amounts, newest first. Q or Escape clears all unrolled bets. Clicking or tapping a placed chip adds another bet to its target. **Right-click a target or chip** to cancel the target’s entire draft wager; Delete/Backspace removes the focused target’s wager too. Three chip shortcuts beside the amount recall the last three distinct successfully placed amounts, newest first. Selecting a shortcut changes the amount without placing a wager. History persists in this browser across refreshes and restarts; unused slots stay empty until you place bets. Remove a wager and place a smaller amount to reduce it. Draft edits spend no Gold.

Each run starts with **100 G and 100 rolls**. Every settled Roll counts, including losses and break-even wagers. Shake does not consume or restore rolls. Your wagers can use your full available bankroll. After roll 100, the final balance becomes the run’s score and betting stops. The leaderboard keeps each player’s best completed score; temporary peaks never post. A bankruptcy before roll 100 ends the run without submitting a score. A results popup opens after either ending. On eligible completion it shows the final score, personal best, and whether this is a first record, improvement, tie, or lower score. A run that enabled probabilities shows its final Gold and explains that no leaderboard score was posted; it cannot replace a previous best. It survives refresh. Set your leaderboard name and choose **Confirm & play again** to save the name and start with 100 G and zero rolls used in one retry-safe action. Early bankruptcy shows that no score was posted. The separate New run button is removed. In Settings, the red **Restart run** button also lets you abandon an unfinished run after confirmation. It discards current progress and bets without submitting a score, and preserves your completed leaderboard record.

**Roll** commits the draft. **Shake** costs no Gold but starts locked on every fresh board. Any nonzero settled gain or loss unlocks one Shake; break-even rolls and draft edits do not count. Shaking changes the probabilities, clears the draft, and locks Shake again. A Jackpot reset and restarting at zero Gold also lock the new board. Hovering or focusing a group highlights its numbers; selected groups stay highlighted. Odds and the Jackpot target are hidden. **Tilt 1–6** is a prominent gold control on the table. Higher means the odds lean toward fewer numbers, without identifying those numbers. Tap it to open the guide’s low/high Tilt explanation. A winning sole wager on the least likely number pays **Jackpot ×24 on every board**, regardless of its probability; the lowest number breaks ties. Any additional positive target removes Jackpot eligibility. A highlighted Rolls remaining card counts down from 100. The Jackpot target stays hidden. A Jackpot hit keeps earned Gold and automatically Shakes. A new run retains the previous best completed score.

The leaderboard is a compact rank, name, and score list on the right on wide screens. It shows the top 10 plus your personal best and the two players directly above you, with your row highlighted and overlapping entries shown only once. Standard rows are 40 px tall. Large scores are abbreviated, with exact values in tooltips and accessible labels. On smaller screens, the trophy button opens the tower from the right. The gear button opens Settings for nickname, sound, motion, and the standard **Show probabilities** switch. Each new run starts with probabilities off. Enabling them opens a confirmation explaining that the current run’s score will not enter the leaderboard, even if probabilities are hidden again. The server saves visibility and that run’s exclusion across refreshes, tabs, and restarts of the server; starting a new run restores eligibility. Existing completed records stay. Probability changes preserve draft bets and do not use rolls or Gold. A gameplay guide opens for a saved player with no previous roll and no dismissed guide; it stays dismissed across refreshes and restarts. The separate **How to play** sidebar control reopens it at any time; Settings contains no guide link. The guide contains the complete rules and preference descriptions: wagering and editing, payouts, starting odds with a 2% floor, random transfers, Tilt, Shake, Jackpot, persistence, and keyboard controls. Essential steps, payout multipliers, Tilt, Shake, Jackpot, and a keyboard reference come first; detailed rules and a numerical example are expandable. The guide has a white reading surface and serif text, with English, Korean, Japanese, Simplified Chinese, Spanish, French, and German versions. It starts in a supported browser language and remembers an explicit selection. Tab moves focus and Enter activates controls; **R rolls and Space Shakes directly after placing a bet, including while a target button has focus**. During play, Space is reserved for Shake. They pause in text fields, editable text, and open dialogs, and ignore modifier combinations, key repeats, and composition. ## Probability model

Fresh boards use a symmetric Dirichlet(1,1,1,1,1,1) draw, scaled to reserve a 2% minimum for each face: `p[i] = 0.02 + 0.88 × w[i]`. All six weights vary; there is no fixed template. After a non-Jackpot payout, a uniform random rate transfers part of the rolled face's probability above 2%. The range follows the pre-roll Tilt: levels 1–6 use **4–8%, 4.2–8.4%, 4.4–8.8%, 4.6–9.2%, 4.8–9.6%, and 5–10%**, respectively. A new five-way Dirichlet draw splits the transfer among the other faces. Misses preserve the board. Bet size and overlapping payouts do not affect the update.

The transfer curve is flatter: the mean rises from 6% at Tilt 1 to 7.5% at Tilt 6. The old middle band is split in two; old levels 4 and 5 become levels 5 and 6, with their concentration boundaries preserved. In 10,000 seeded starts per policy, the new Tilt 5 lasts a median three rolls when betting the initially strongest face and four with rotating group bets; Tilt 6 lasts two and four, respectively. Full coverage changes the board on every roll and produces two-roll medians at both upper levels. These are pacing targets, not guaranteed minimums. Reproduce the comparison with `npm run test:balance`.

Tilt uses Shannon entropy and converts the effective number of outcomes into six levels. It reveals concentration, not a favored face, group probability, or expected profit. See [the probability model](docs/PROBABILITY_MODEL.md) for formulas, level boundaries, and tuning results.

The server persists a single Shake entitlement. A settled nonzero result unlocks it; later break-even rolls do not revoke it, and gains followed by losses still count even if the balance returns to its previous value. A manual or automatic reset consumes it. Ending a run disables Shake. Nonempty legacy endless-game databases now fail startup without changing their saves or receipts; retain that database with its previous release or select a new `DB_PATH`. Current competition saves persist normally. Schema version 2 added the previous personal best used by the results popup; version 3 added a moderation flag and a partial ranking index; version 4 adds per-run probability visibility and leaderboard eligibility. These migrations preserve all competition players, scores, and receipts. A database from a newer schema is rejected rather than downgraded. Legacy completed runs compare against their saved best because their earlier best was not recorded. Browser sound and motion preferences remain local. Probability visibility and run eligibility are saved on the server.

Break-even and net-loss returns retain their accurate result labels without a victory banner. Reduced motion skips movement and particle effects. Large chip labels are abbreviated; the target's accessible name and tooltip retain the exact wager.

Gold, wagers, returns, records, and revisions use **BigInt** internally and canonical decimal **strings** in JSON and SQLite. Scores sort by decimal string length, then lexical value, so ranking works beyond both JavaScript's safe integer range and SQLite's 64-bit integer range. No gameplay score cap is imposed. Probability values use unrounded IEEE-754 doubles; probability labels show up to two decimals when enabled. Hidden values are omitted from target labels and accessible names. This is presentation hiding: the API still returns the odds to the client. Labels never feed settlement. The outcome sampler uses the stored weights' sum to absorb floating-point roundoff; it does not smooth the probabilities.

The server generates cryptographic random numbers and anonymous 256-bit session cookies, storing only their hashes. An action carries its expected revision, a unique request ID, and a player binding. Requests saved by older clients without that binding remain compatible with the existing receipt fingerprint. A SQLite `BEGIN IMMEDIATE` transaction checks the revision, settles, increments the roll count, updates the best completed score only on roll 100, and stores the complete response together. Reusing an ID with the same request returns the original receipt; reusing it for different data is rejected. Stale requests return the latest board without settling. Receipts are retained indefinitely for retry safety.

Uncommitted drafts belong to the current tab and clear on refresh, settlement, or Shake. The active game and last settled result are durable. The client saves a pending action in session storage before sending it, and recovers the same request after a network interruption or reload. Cross-tab updates invalidate the draft. Visible tabs synchronize state five seconds after the preceding read finishes, with an immediate check on focus, visibility recovery, or a same-player cross-tab hint. Reads share one in-flight request and use private ETag revalidation. The visible leaderboard refreshes at most every 30 seconds, plus after a nickname or completed record changes; a closed mobile drawer does not fetch it. Successful ordinary actions use their committed response directly. Recovery retries also read the latest state because an old receipt may precede another tab’s actions. Hidden tabs stop polling and finish decorative motion without changing the committed game. Reads time out after eight seconds, back off after transient failures, and stop automatic retries after six failures until Reconnect, focus, or an online event. Leaderboard failures have their own 30–120-second backoff and six-attempt bound. Mutations have a 12-second timeout, preserve their exact pending request on uncertain errors and throttling, and retry only by user action or one saved-request recovery on reload. Retry delays survive reload. Unavailable browser storage uses in-memory preferences and in-tab recovery; that pending request cannot survive closing the tab.

The leaderboard shows the top 10 players by their best **final Gold after 100 rolls**, plus the current player and up to two immediately higher ranks wherever they fall in the full ranking. Entries shared with the top 10 are not repeated; a gap separates nonadjacent ranks. Ties use stable player-ID ordering. A player has no ranked score until completing all 100 rolls. A final score below 100 G, including zero on roll 100, is valid; bankruptcy earlier posts nothing. Later unfinished or lower-scoring runs do not replace a completed best. Names need not be unique. The results popup restarts ended runs; Settings can discard an active run after confirmation.
